# AIID: Product Strategy

20.11.2026. Решения ниже — рекомендации, а не разрешение менять реализацию. Источники, роли и доказательства собраны в [Discovery Matrix](DISCOVERY_MATRIX.md); процесс — в [AS-IS / TO-BE](AS_IS_TO_BE.md).

## Продуктовое обещание

**Product Vision:** помочь сотруднику AIID превращать описание задачи в короткий, проверяемый список экспертов, сохраняя окончательное решение за человеком.

**Problem Statement:** согласно ТЗ, нужная экспертиза уже есть в Альянсе, но её поиск зависит от личных контактов и занимает дни. Пользователю приходится искать человека, не имея удобного способа сопоставить запрос с профилями. Длительность и причины задержек пока не измерялись командой.

**Value Proposition:** один текстовый запрос → ранжированные кандидаты из реестра → основания и ограничения каждого совпадения. Потенциальная ценность — меньше ручных обращений при составлении списка, более понятное сравнение и меньшая зависимость от знания конкретных людей. Это ожидаемый эффект, не доказанная экономия.

**USP для этого контекста:** локальный поиск по внутреннему реестру с отраслевыми синонимами, доступностью и проверяемым объяснением без внешнего AI API. Это сочетание требований AIID, а не доказанное уникальное предложение на всём рынке. Семантический поиск не является нашим изобретением и сейчас в MVP не реализован.

### Jobs To Be Done — гипотезы для проверки

| Когда | Я хочу | Чтобы |
|---|---|---|
| Поступает инженерная или отраслевая задача | Описать её своими словами и увидеть подходящих людей | Быстро получить список для дальнейшей проверки |
| Несколько кандидатов выглядят похожими | Сравнить компетенции, отрасль, город, опыт и занятость | Понять различия и выбрать, с кем связываться |
| Полного совпадения нет | Увидеть, какие условия не выполнены | Осознанно уточнить задачу, а не принять ложную рекомендацию |

**Зачем интеллектуальный поиск:** свободный текст нужно сопоставить с нормализованными названиями компетенций и несколькими условиями, затем упорядочить найденное. CSV хранит записи, но не выполняет этот сценарий сам. Сейчас это классический information retrieval: BM25, стемминг, словарь и правила ранжирования. Это не обученная семантическая модель и не LLM. Дополнительный ML оправдан только измеримым улучшением незнакомых формулировок без ухудшения условий, задержки и офлайн-работы.

## MVP scope и критерии AIID

Критерии кейса: качество 30%, объяснения 15%, сквозная работа 15%, скорость 10%, доступность 10%, UI 10%, бонусы 10%. Это критерии AIID; не смешивать их с общей таблицей METU. По ТЗ отсутствие порога качества или объяснений закрывает первое место. [Официальный раздел AIID](https://hackathon.metu.kz/).

| Приоритет / требование | Состояние текущего MVP | Что осталось подтвердить |
|---|---|---|
| Must: CSV UTF-8, 100+ профилей | CLI-importer, валидация, 120 синтетических записей | Воспроизводимый запуск на ноутбуке для защиты; понятность загрузки оператору |
| Must: текстовый поиск | API принимает естественный текст, русская нормализация и словарь | Живой ввод через UI; неизвестные термины, отрицания и сложные условия |
| Must: top-3 | API ранжирует и возвращает до указанного limit, от 3 до 20 | Не выдавать пустые/нерелевантные профили ради количества; согласовать поведение при нехватке кандидатов |
| Must: объяснения | Совпавшие навыки, отрасль профиля, условия и missing_requirements | Отображение на UI и отсутствие неподтверждённых выводов |
| Must: офлайн | Docker + PostgreSQL + локальный retrieval, без model API | Полный UI→API сценарий при отключённом внешнем интернете, включая холодное открытие страницы |
| Must: порог Hit@3 | Предыдущие внутренние прогоны успешны | Неизвестные заранее запросы и независимая разметка; официальный тест ещё не пройден |
| Should: занятость | Статусы и штраф ранжирования | Правильное отображение; кто и когда обновляет реальные статусы |
| Should: отраслевой фильтр | API поддерживает дополнительный жёсткий фильтр | Работает поверх текста, не вместо него |
| Should: matching score | Доля распознанных условий с явной формулой, не вероятность | Не показывать 100% как понимание всего запроса; отобразить неизвестные слова |
| Could: востребованные навыки | Не реализовано, логи запросов не собираются | Только после основного сценария; заранее определить агрегацию и правила хранения |
| Could: feedback | Не реализовано | Договориться, что значит «не подошёл»; не превращать единичный клик в автоматическое переобучение |
| Could: казахский / аналитика | Казахский поиск не подтверждён | Не обещать многоязычность только по языкам в профилях |

Нет scope на хакатон: биржа труда, социальная сеть, подбор на вакансии, биллинг, календарный сервис и интеграции внешних экспертных баз. Функциональность frontend не считается готовой без интеграционного показа.

## Приоритетный backlog

Это список предлагаемых действий. В рамках Discovery код, данные и инфраструктура не меняются.

| Очерёдность | Изменение | Почему сейчас | Приёмка | Ответственный по роли |
|---|---|---|---|---|
| P0.1 | Независимый набор, анализ ошибок и затем точечные улучшения понимания запроса | Качество — 30% и условие первого места; известные эталоны недостаточны | Зафиксировать разметку до поиска; выполнить протокол ниже; исправления оценивать на отдельном наборе | Жандос организует разметку, Рахат анализирует |
| P0.2 | Завершить UI→API и сравнение кандидатов | Сквозная работа 15%, объяснения 15%, UI 10% | Произвольный запрос, три карточки при наличии релевантных людей, missing/unknown/no-match состояния, синтетическая пометка | Рахат + AI-ассистент, QA Жандос |
| P0.3 | Проверить офлайн-демо и подготовить честные метрики | Скорость 10%, обязательная надёжность | Отключить внешнюю сеть, перезагрузить UI, выполнить новый запрос; сохранить результат и видео | Вся команда |
| P1.1 | Сделать статус и ограничения понятными; определить актуальность реестра | Доступность — 10%; устаревшая запись обесценивает подбор | В демо видна занятость; у пилота есть предложенный куратор и порядок подтверждения статуса | Рахат + AI-ассистент; владелец данных AIID ещё не назначен |
| P1.2 | Проверить операторы «и/или/без», город, опыт и неизвестные условия | Цена ложного полного совпадения выше декоративной функции | Нет тихо потерянных обязательных условий на независимых кейсах | Рахат после согласования изменений |
| P2 | Локальные embeddings, feedback или дашборд | Только после Must/Should и подтверждённой потребности | Измеримое улучшение при сохранении offline baseline; без скачивания весов без разрешения | Алмас — локальная Qwen; остальные расширения — по решению команды |

**Три наиболее ценных улучшения:** точность на неизвестных формулировках; законченный экран обоснованного выбора; актуальные и подтверждаемые данные о компетенциях/доступности. Первое требует слепой проверки, второе — интеграции, третье — договорённости о процессе, а не новой большой модели.

## Валидация и метрики

### Что уже наблюдалось

| Показатель | Доказательство и граница |
|---|---|
| 120 профилей | Подтверждено чтением CSV; 8 отраслей, 6 городов, 38 уникальных наборов навыков |
| 16 backend-тестов | Пройдены в предыдущем запуске на PostgreSQL; это тесты поведения, не исследование пользователей |
| Hit@3 = 7/7 | Семь эталонов команды; не независимый тест AIID |
| Hit@3 = 21/21 | Перефразировки и новые комбинации команды; все 7 эталонных expert ID встречаются и здесь |
| PostgreSQL API: максимум около 45 мс | Предыдущая in-process оценка, включая БД и сериализацию, без HTTP/UI; не сравнивать напрямую со временем ручного назначения |
| Один последующий HTTP-запрос около 35 мс | Предыдущий smoke-check контейнерного API; одного наблюдения недостаточно для p95 или SLA |
| Полностью офлайн UI | Не подтверждено. Запрет Python socket.connect в тесте не равен отключению интернета и не покрывает frontend |
| Экономия времени, стоимость, назначения | Не измерены; заявлять проценты или ROI нельзя |

Новые тесты сейчас не запускались. `tmp/*-report.json` — ранние отчёты SQLite, а не свежий PostgreSQL-протокол. Для питча нужен новый сохранённый отчёт команды на финальной версии после отдельного разрешённого этапа проверки.

### Предлагаемый независимый протокол, ещё не выполнен

1. Человек, не писавший поиск и эталоны, составляет **20 положительных запросов и 5 сценариев отказа/неполного соответствия** по неизменённому CSV. Сначала фиксирует все подходящие ID и жёсткие условия, затем видит выдачу. Лучше привлечь ментора для части разметки; участия ментора пока нет.
2. В положительные запросы включить 5 перефразировок без копирования названий навыков, 5 сочетаний нескольких обязательных компетенций, 5 случаев с городом/опытом/занятостью и 5 ранее не проверенных сочетаний. Группы — дизайн теста, не полученные результаты.
3. Отдельно проверить отсутствие профиля, известный город при неизвестной специальности, противоречивые условия, частичное соответствие и нераспознанный термин. Не смешивать эти случаи с обычным Hit@3: правильный отказ тоже ценен.
4. До просмотра результатов зафиксировать релевантность и правило учёта busy-эксперта. Не менять labels после того, как увидели порядок. Сохранить исходный запрос, фильтр, top-3, объяснения, parsed_query, версию кода и данных.
5. Если по результатам меняются словарь или ranking, это становится development-набором; финальную оценку проводить на новых, не использованных при исправлениях запросах.

| Метрика | Как измерять | Предлагаемый порог, не результат |
|---|---|---|
| Hit@3 | Доля положительных запросов, где top-3 пересекается с заранее размеченными relevant IDs | ≥80%, то есть ≥16/20; официальный формат дополнительно проверяет ≥4/5 |
| Пригодность выдачи | Сколько кандидатов нарушает жёсткое условие; доля релевантных среди трёх | Не допускать нарушения, помеченного как full; порог пригодности согласовать с ментором |
| Объяснения | Сверить каждый matched_skill/industry с профилем, missing — с условиями, предупреждения — с текстом | 0 неподтверждённых утверждений в проверенной выборке |
| Отказы | Отдельная доля верных no-match и честных partial | Все подготовленные отрицательные сценарии без ложного полного совпадения |
| Скорость | Считать UI→последняя карточка; отдельно API; median/p95/max, холодный и повторный запрос | Каждый проверенный сквозной запрос ≤30 с; без обещаний о неизмеренных нагрузках |
| Офлайн | После установки образов отключить внешнюю сеть; сохранить локальную связь Docker↔PostgreSQL; перезагрузить UI и ввести новый запрос | Сценарий выполняется без загрузок CDN/API; health.offline сам по себе не доказательство |
| Бизнес-эффект | В пилоте сравнить одинаковые задания вручную и с системой; время до пригодного списка и до подтверждённого контакта | Порог согласует AIID после измерения baseline; конкретная экономия пока неизвестна |

## Решение на оставшееся время

Стабилизировать основной сценарий и доказательства. Не оптимизировать миллисекунды уже быстрого backend ценой риска интеграции. Незнакомые требования, неверно прочитанный процент и неактуальная доступность — более значимые продуктовые риски, чем отсутствие дашборда.
